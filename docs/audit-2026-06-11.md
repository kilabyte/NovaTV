# NovaTV Stability Audit

Date: 2026-06-11

Scope: full codebase (78 Dart files, ~17k lines, generated files excluded). Ten subsystem-focused audit passes covering the player, EPG data and UI, playlist parsing, Riverpod state, Hive storage, async correctness, app shell and startup, rebuild performance, and network/error handling. Every finding below was independently re-read and adversarially verified against the actual code; 4 candidate findings were refuted and removed.

Confirmed findings: 67 (7 high, 27 medium, 33 low)

## High severity

### HIGH-1: Entire EPG download buffered in memory, then duplicated by redundant Uint8List.fromList copy

Location: `lib/features/epg/data/datasources/epg_remote_data_source.dart:34`  
Category: performance | Verifier confidence: high

Impact: XMLTV feeds are commonly 50-500MB decompressed. The full response is buffered (ResponseType.bytes), then Uint8List.fromList makes a second full copy of a buffer that is already a Uint8List, then gzip.decode + utf8.decode produce the full decompressed string, then compute() copies that string again into the isolate. Peak memory is 3-4x the EPG size simultaneously, which OOM-kills the app on Android TV and mobile devices with large provider EPGs.

Suggested fix: Drop the redundant copy (use response.data directly, it is already a Uint8List), and move gzip decode + utf8 decode into the parse isolate so the main isolate never holds the decompressed string. Longer term, switch to ResponseType.stream with a streaming gzip/XML pipeline.

Verification notes: Confirmed. epg_remote_data_source.dart:25-34 buffers the whole response with ResponseType.bytes, then Uint8List.fromList(response.data ?? []) makes a second full copy of a buffer Dio already returns as a Uint8List (typed List<int>). xmltv_parser.dart:16-36 then does content = utf8.decode(gzip.decode(bytes)) (full decompressed buffer plus a UTF-16 Dart string that is up to 2x the byte size) and compute(parseXmltvContent, ParseXmltvParams(content: content, ...)), and isolate message passing copies the string again. Peak memory of several multiples of the decompressed EPG size simultaneously is accurate. The project explicitly targets Android TV (recent 'android tv: full Leanback support' commit), where boxes commonly have 1-2 GB RAM, so OOM on large provider feeds is a realistic outcome. High severity stands, with the caveat that small/medium EPGs are unaffected.

### HIGH-2: Gzip decompression and UTF-8 decode of entire EPG file run on the main isolate; full string then deep-copied into compute isolate

Location: `lib/features/epg/data/parsers/xmltv_parser.dart:22`  
Category: performance | Verifier confidence: high

Impact: Real-world XMLTV .xml.gz feeds decompress to 100-500 MB. gzip.decode + utf8.decode of that on the main isolate freezes the UI for seconds (ANR risk on Android/Android TV, directly contradicting the 'prevents UI blocking' comment). Peak memory is roughly bytes + decompressed UTF-16 string + a second full copy for the isolate + the XML DOM + result maps, easily >1 GB, causing OOM kills on TV boxes during EPG refresh.

Suggested fix: Move gzip decode and utf8 decode inside the compute entry point (pass the raw Uint8List, which transfers cheaply), or better, switch to a streaming SAX-style parser (xml package XmlEventDecoder) fed from a Dio response stream so the document is never fully materialized.

Verification notes: Verified: xmltv_parser.dart:22 runs `utf8.decode(gzip.decode(bytes))` synchronously inside parseBytes, which is awaited from EpgRemoteDataSourceImpl.fetchEpg (epg_remote_data_source.dart:39) on the main isolate, no compute wrapper exists anywhere upstream (checked epg_repository_impl.dart:25 and all callers via grep). Only the XML parse at line 36 is offloaded, and it sends the full decoded string inside a custom ParseXmltvParams object over a SendPort, which copies it into the spawned isolate. The data source buffers the entire response with ResponseType.bytes; no streaming. The 'prevents UI blocking' comment is contradicted for the decompress/decode step. The specific MB/GB figures are estimates, but the mechanism (multi-second main-isolate freeze plus several simultaneous full copies of a large feed) is real, and the app explicitly targets Android TV where ANR/OOM on low-RAM boxes is plausible, so high severity stands.

### HIGH-3: setState on every 16px of horizontal scroll rebuilds the entire TV Guide screen (rebuild storm)

Location: `lib/features/epg/presentation/screens/tv_guide_screen.dart:268`  
Category: performance | Verifier confidence: medium

Impact: During a fling across the 36,960px-wide grid (168h x 220px), a frame moves far more than 16px, so this fires essentially every frame. Each fire rebuilds the whole screen including non-grid chrome, causing jank on large playlists, especially on Android TV class hardware. The 16px threshold also fights the sticky-text feature it exists for (text jumps in 16px steps).

Suggested fix: Move _currentScrollOffset into a ValueNotifier<double> and have only the widgets that need it (sticky-text cells and the time header) listen via ValueListenableBuilder, instead of setState on the screen-level State.

Verification notes: Confirmed mechanism. _onScrollOffsetChanged (lines 262-273) calls setState on _TvGuideScreenState, dirtying the root build: _buildHeader with the date-chip ListView, _buildTimeHeaderItems' List.generate(_totalHours=168) at line 756, _buildChannelColumn, and every visible program row via _buildProgramRow. During a fling on the 36,960px grid, per-frame deltas far exceed 16px, so this fires essentially every frame. Note a normal horizontal SingleChildScrollView scroll would only repaint (translate), not rebuild, this design converts every scroll frame into a full-screen rebuild, which is the load-bearing point. RepaintBoundaries limit repaints but not widget construction/element diffing. Severity 'high' is defensible given the app explicitly targets Android TV class hardware (recent Leanback commit) and this is the guide's primary interaction. Confidence medium only because actual jank depends on hardware; the mechanism is certain.

### HIGH-4: Rapid channel zapping uses a disposed Player and clobbers the new channel's state (no generation guard in playChannel)

Location: `lib/features/player/presentation/providers/player_providers.dart:225`  
Category: race-condition | Verifier confidence: high

Impact: playChannel() awaits repository.getChannel() with only a 'mounted' check, which guards the notifier, not the request. If a second playChannel (rapid zapping via L/channelUp/pageDown shortcuts, mini-player taps, or app_shell.dart:327) or stop() runs during that await, it disposes the locally-captured 'player'. The stale continuation then (a) sets state.copyWith(channel: channelA) on top of channel B's freshly-created player state, so the UI shows channel A's name/EPG while playing B, and (b) calls player.open() on a disposed Player, which throws (caught and written as a bogus 'Failed to start playback' error onto the NEW channel's state) or asserts in debug. The same hole lets PlayerScreen._initializePlayer double-start: state.channel is only set after getChannel resolves, so its 'channel?.id != widget.channelId' check passes twice for the same channel during load.

Suggested fix: Add a generation/epoch counter: increment it at the top of playChannel and in stop(), capture it locally, and bail out after every await if it changed (or check identical(state.player, player) before each state write and before _openWithMimeFallback). Apply the same guard inside the result.fold success closure.

Verification notes: Confirmed in player_providers.dart:121-255. playChannel awaits stop() and repository.getChannel() with only an 'if (!mounted) return' check, which guards notifier disposal (Riverpod keeps this global provider alive anyway), not supersession by a newer call. A second playChannel during the getChannel await runs stop(), which disposes state.player (the first call's locally captured 'player') and cancels subscriptions. The first call's continuation then executes state.copyWith(channel: channelA) over the second call's state and calls _openWithMimeFallback(player, ...) on the disposed Player; the throw is caught at line 248-252 and written as 'Failed to start playback' onto the new channel's state. Real interleaving via genuine awaits, not an imagined thread race. Zap triggers exist (playPreviousChannel bound to L/channelUp/channelDown/pageUp/pageDown in player_screen.dart:215-226, plus app_shell.dart:327 and several screens). Severity corrected from critical to high: the disposed-player open is caught (no crash), there is no data loss, and one more zap recovers; the impact is wrong channel metadata and a spurious error banner.

### HIGH-5: EXTINF regex splits on first comma, breaking quoted attribute values containing commas

Location: `lib/features/playlist/data/parsers/m3u_parser.dart:8`  
Category: logic | Verifier confidence: high

Impact: Commas inside quoted attributes (group-title="USA, News" is extremely common in real IPTV playlists) produce garbage channel names, lose tvg-name/group-title/logo extraction, break EPG matching, group filtering, and the favorite-preservation key (tvgId|name|group) used during refresh, so favorites on affected channels are also silently lost on refresh.

Suggested fix: Split attributes from the display name at the LAST comma that is outside double quotes (e.g. scan the line tracking quote state, or use a regex like r'^#EXTINF:\s*(-?\d+(?:\.\d+)?)\s*((?:[^"\n,]|"[^"]*")*),\s*(.*)$' that treats quoted segments as atomic).

Verification notes: Reproduced with a real Dart test: for '#EXTINF:-1 tvg-id="cnn" tvg-name="CNN, HD" group-title="USA, News",CNN HD' the lazy (.*?) in lib/features/playlist/data/parsers/m3u_parser.dart:8 stops at the first comma (inside the quoted tvg-name), producing attrs=[tvg-id="cnn" tvg-name="CNN] and name=[HD" group-title="USA, News",CNN HD]. The truncated attrs string then fails the tvg-name and group-title quoted-value patterns (both returned null in the test), so name, group, and logo extraction break exactly as claimed; EPG matching and group filtering for affected channels are broken. One impact sub-claim is wrong: favorites are NOT lost on refresh. The preservation key at playlist_repository_impl.dart:147 is tvgId|name|group, and the same buggy parser produces the same garbage name/group on every parse, so old and new keys match deterministically. The core defect and its main user-visible impact (garbage names, lost grouping, broken EPG matching for commas-in-quotes playlists, which are common) stand, so high severity is warranted.

### HIGH-6: toggleFavoriteProvider runs its mutation in a cached Provider, so the channel-list star only works once per channel per session

Location: `lib/features/playlist/presentation/providers/playlist_providers.dart:342`  
Category: bug | Verifier confidence: high

Impact: In the channel list, tapping a channel's favorite star works the first time only; every subsequent tap on the same channel that session is a silent no-op, so users cannot un-favorite (or re-favorite) a channel from the list until app restart. Other screens (favorites, search, player) call the notifier directly and are unaffected.

Suggested fix: Delete toggleFavoriteProvider and call ref.read(favoriteNotifierProvider.notifier).toggleFavorite(id) directly from channel_list_screen.dart:259, matching every other call site.

Verification notes: Confirmed. playlist_providers.dart:342 defines a non-autoDispose Provider.family whose create callback calls toggleFavorite as a side effect. In Riverpod 2.6.1, non-autoDispose family elements are created on first read and cached per parameter for the container's lifetime; the provider watches nothing and is never invalidated anywhere in lib/ (grep confirms the only consumer is channel_list_screen.dart:259 via ref.read). FavoriteNotifier's invalidations (favoriteChannels/allChannels/filteredChannels) do not touch this family. So the second tap on the same channel's star returns the cached null without re-running the body, making un-favoriting from the channel list impossible until restart. Other screens (favorites_screen.dart:88, search_screen.dart:205, player_screen.dart:138) call the notifier directly and are unaffected, exactly as claimed.

## Medium severity

### MEDIUM-1: safeOpenBox retry path closes a fully-open box that other code is actively using

Location: `lib/core/storage/hive_storage.dart:23`  
Category: race-condition | Verifier confidence: high

Impact: Code elsewhere holding the Box reference (cached in HiveStorage._openBoxes, WindowService._settingsBox, AppSettingsNotifier._box, RecentlyWatchedNotifier._box, or mid-iteration loops) throws 'Box has already been closed' on its next get/put, losing writes (e.g., settings saves, window geometry) or aborting index builds.

Suggested fix: Only close-and-retry on lock/IO errors (inspect the exception); rethrow immediately on HiveError type mismatches. Better: never close a box the helper did not itself half-open, and unify all opens of a given box name behind one typed accessor.

Verification notes: Mechanism confirmed and reachable. hive_ce 2.15.1 (hive_impl.dart:227) uses an exact valueType == E check, so requesting an open box with a different type parameter throws HiveError even between Box<dynamic> and Box<T>. The codebase has exactly such a mismatch: 'epg_metadata' is opened untyped at index_service.dart:161 and :249 but typed as Box<EpgMetadataModel> at index_service.dart:70 and epg_local_data_source.dart:69. bootstrap.dart:40 fires buildAllIndexes (untyped open) concurrently with startup EPG auto-refresh saveEpgData (typed open), so safeOpenBox's catch block (hive_storage.dart:23-29) routinely closes a healthy open box out from under the other holder and reopens it with the new type; a holder mid-iteration (e.g. the metadataBox.keys loop at index_service.dart:170 with awaits inside) then throws 'Box has already been closed'. However, the claimed blast radius is exaggerated: 'playlists', 'channels', 'app_settings', 'settings_box' (untyped in both WindowService and HiveStorage.openSettingsBox), 'recently_watched', and all index boxes are opened with consistent type parameters, so for them the catch only fires on genuine open failures where the box is NOT open and close is a no-op. Settings saves and window geometry are not at risk. Practical damage is limited to epg_metadata type ping-pong: aborted EPG index builds and transient errors in EPG flows, all caught and logged. High/race-condition is corrected to medium.

### MEDIUM-2: Untyped open of shared 'epg_metadata' box conflicts with typed opens, causing HiveError and forced close of an in-use box

Location: `lib/core/storage/index_service.dart:161`  
Category: race-condition | Verifier confidence: high

Impact: First getEpgMetadata/saveEpgData/deleteEpgData after startup throws HiveError; safeOpenBox's retry then force-closes the globally shared box (hive_storage.dart:25) and reopens it typed. Any concurrent holder (IndexService._buildEpgIndexes iterating metadataBox.keys across awaits at index_service.dart:170-178) then hits 'Box has already been closed', its catch swallows it, and EPG indexes are silently never built. The two type conventions can ping-pong close/reopen the box repeatedly.

Suggested fix: Open 'epg_metadata' with the same type parameter everywhere: change index_service.dart:161 and :249 to safeOpenBox<EpgMetadataModel>('epg_metadata').

Verification notes: Verified against both the app code and hive_ce 2.15.1 source in the pub cache. index_service.dart:161 and :249 call safeOpenBox('epg_metadata') with E=dynamic while index_service.dart:70 and epg_local_data_source.dart:69/200/219/225 open the same box as Box<EpgMetadataModel>. hive_impl.dart _openBox short-circuits to box(name) when already open, and _getBoxInternal throws HiveError when box.valueType != E, which mismatches in both directions (dynamic vs EpgMetadataModel). safeOpenBox's catch (hive_storage.dart:18-29) then force-closes the shared box and reopens it with the requested type. bootstrap.dart:40 fires buildAllIndexes() unawaited, so the untyped open genuinely interleaves with startup EPG refresh and TV Guide typed opens; the throw/close/reopen cycle is deterministic for any typed access after the index build opens the box untyped. Downgraded from high to medium: safeOpenBox recovers each individual call (100ms delay + reopen), the metadata box is tiny, and the worst secondary effect (the swallowed catch at index_service.dart:181 silently skipping EPG index builds) only degrades reads to the existing full-scan fallback paths in epg_local_data_source rather than breaking features.

### MEDIUM-3: Startup and resume index builds load every EPG program box fully into RAM and scan them synchronously on the main isolate

Location: `lib/core/storage/index_service.dart:191`  
Category: performance | Verifier confidence: high

Impact: On a cold start with missing/stale indexes (e.g., after the partial-index or type-mismatch failures above), the UI freezes for seconds while hundreds of thousands of ProgramModels are deserialized and grouped on the main isolate, and the entire multi-playlist EPG dataset stays resident in RAM for the life of the app even if the TV Guide is never opened.

Suggested fix: Reuse the existing compute-isolate path (epg_local_data_source._buildProgramIndexes) from IndexService instead of HiveIndexHelper.buildIndex, and close program boxes after index building (or open them as LazyBox) so resume validation does not pin the full EPG in memory.

Verification notes: Confirmed. _buildProgramIndexesForPlaylist (index_service.dart:191) calls safeOpenBox<ProgramModel> BEFORE its indexExists guard, so even warm launches with valid indexes fully open (and deserialize, since the box is non-lazy) every program box; validateIndexesOnResume (index_service.dart:76) does the same on every app resume just to check isNotEmpty. When indexes are missing, HiveIndexHelper.buildIndex (hive_index_helper.dart:53-63) iterates every key with get() in a synchronous main-isolate loop, in deliberate contrast to the data source's own _buildProgramIndexes which uses a compute isolate (epg_local_data_source.dart:272-275 comment explicitly cites this cost). No code path ever closes these boxes, and the file's own comment (index_service.dart:187-188) acknowledges 100MB+ program boxes, so the RAM-residency and main-isolate jank claims hold. Medium severity is appropriate: it is a real performance defect but the worst case requires missing/stale indexes plus a large EPG dataset.

### MEDIUM-5: Channels sharing a tvg-id (HD/SD/FHD variants) collide in epgIdToChannelId, only the last channel gets guide data

Location: `lib/features/epg/data/compute/epg_compute.dart:42`  
Category: logic | Verifier confidence: high

Impact: IPTV playlists routinely list 'Channel HD', 'Channel SD', 'Channel FHD' variants sharing one tvg-id. In the TV guide only the last-listed variant shows programmes; all sibling variants render as empty rows even though EPG data exists for them.

Suggested fix: Make the mapping one-to-many: `Map<String, List<String>> epgIdToChannelIds`, and append each matched program to every channel id registered under that epg id.

Verification notes: Confirmed. epg_compute.dart:39-49 builds a String->String map where every write is last-writer-wins per epgId key. Channel ids are guaranteed unique per playlist entry (m3u_parser.dart:239 generates '${playlistId}_$channelIndex', with a comment explicitly noting 'tvg-id can be duplicated across different groups'), so two variants sharing a tvg-id always have distinct channel.id values and the earlier one is overwritten. Programs are routed via epgIdToChannelId[program.channelId] (line 58) to that single surviving id, and the TV guide row lookup at tv_guide_screen.dart:850 is programsByChannel[channel.id] ?? [] with no epgId fallback, so all sibling variants render empty rows. The synchronous copy at tv_guide_screen.dart:192-208 has the identical structure. No dedup of channels by epgId occurs before the grid is built (channels list is passed straight to _buildProgramGrid at line 656). Other surfaces (channel cards, now-playing) use epgId-keyed maps and are unaffected, but the guide-grid claim stands. Medium severity is appropriate.

### MEDIUM-6: XMLTV timezone offset without a space separator is silently dropped, shifting all program times

Location: `lib/features/epg/data/compute/xml_parse_compute.dart:189`  
Category: bug | Verifier confidence: medium

Impact: Every programme from such a feed is offset by the timezone amount (e.g. 1-12 hours). The guide grid, 'now playing' and next-program logic all show the wrong shows with no error, since the parse 'succeeds'.

Suggested fix: Detect the offset with a regex against the tail of the string (e.g. RegExp(r'([+-]\d{4})$')) before splitting on space, so both 'YYYYMMDDHHMMSS +HHMM' and 'YYYYMMDDHHMMSS+HHMM' forms are honored.

Verification notes: Confirmed in code. _parseXmltvDate (xml_parse_compute.dart:189) only extracts tzOffset when dateStr.indexOf(' ') > 0. For '20260611120000+0100', spaceIndex is -1, tzOffset stays null, padRight(14) is a no-op on the 19-char string, substring(0,4) through substring(12,14) parse only the first 14 digit characters, and DateTime.utc at line 205 treats the stamp as UTC, silently discarding '+0100'. No exception is thrown so the catch block never fires and the parse 'succeeds' with times shifted by the full offset, affecting the guide grid and now/next logic. Confidence is medium rather than high only because the XMLTV DTD mandates a space before the offset, so impact depends on the user's feed using the non-conforming no-space variant, which does occur in the wild but I could not verify against an actual feed sample in the repo. Medium severity is fair given silent, systematic time shifts when triggered.

### MEDIUM-7: Fire-and-forget index rebuild races readers and swallows failures, leaving Hive program index permanently stale

Location: `lib/features/epg/data/datasources/epg_local_data_source.dart:75`  
Category: race-condition | Verifier confidence: high

Impact: After saveEpgData returns (and providers invalidate/re-read), the on-disk index still contains the PREVIOUS refresh's program IDs until the unawaited rebuild lands. getProgramsForChannel/getProgramsInRange/getCurrentProgram take the indexed path because indexedKeys.isNotEmpty, box.get() returns null for IDs that no longer exist, and newly added programs (new IDs) are invisible. If the rebuild throws (e.g. box open failure), the double-swallowed error means the index stays stale forever: the TV guide and now/next overlays silently show missing or partial program data with no error and no fallback.

Suggested fix: Await the index rebuild inside saveEpgData (or at minimum clear both index boxes synchronously before returning so readers fall back to full scan), and log the swallowed exception. Alternatively store a fetchedAt stamp in the index box and have getIndexedKeys treat a mismatched stamp as 'no index'.

Verification notes: Mechanism confirmed: epg_local_data_source.dart:75 does not await _buildProgramIndexes and swallows errors twice (.catchError at 75-78 plus catch(_) at 292-294), and all three indexed readers (getProgramsForChannel:94, getProgramsInRange:137, getCurrentProgram:174) take the indexed path whenever indexedKeys.isNotEmpty with no staleness detection, the full-scan fallback only runs for an empty index. However the impact is overstated: program IDs are deterministic ('${channelId}_${start.millisecondsSinceEpoch}' in xml_parse_compute.dart:176), so after a refresh most stale index keys resolve to the NEW models in the box (same key). What is actually lost during the window is newly added programs (e.g. the new leading day of the 7-day range) and shifted start times, not the whole guide. And 'permanently stale forever' is wrong: every subsequent saveEpgData retries the rebuild, so a swallowed failure persists only until the next successful refresh. Real bug (should await or add staleness fallback), but medium not high.

### MEDIUM-8: saveEpgData clear-then-putAll is non-atomic: crash loses entire EPG dataset and readers see an empty guide during refresh

Location: `lib/features/epg/data/datasources/epg_local_data_source.dart:54`  
Category: bug | Verifier confidence: high

Impact: If the app is killed or crashes between clear() and putAll() completing, all EPG data for that playlist is permanently gone until the next successful network refresh. During every refresh there is a multi-second window where getProgramsInRange/getCurrentProgram read an empty box, so the TV Guide blanks out and now/next info disappears while watching.

Suggested fix: Write new data into a temporary box (e.g. epg_programs_<id>_staging), then atomically swap by deleting the old box and renaming, or at minimum putAll the new map first using deterministic ids (they are channelId_startMs) and then deleteAll the keys not present in the new map, avoiding the empty window entirely.

Verification notes: Pattern confirmed at epg_local_data_source.dart:54-66: programsBox.clear() then putAll() with no temp-box swap. The reader-window half is real and reachable: currentProgramsProvider/currentProgramProvider re-read every minute via minuteTickProvider (epg_providers.dart:96-128), and putAll of a large program map awaits I/O so reads interleave; worse, during the window the OLD index is still non-empty, so box.get(key) returns null for cleared entries and readers return empty with no fallback. The crash-loss half is real but self-healing, not 'permanent': EPG is a re-fetchable cache, and metadata (fetchedAt) is only written AFTER putAll (line 69-71), so a crash mid-write leaves stale metadata and the startup auto-refresh re-fetches. EpgRefreshNotifier also already dedupes concurrent refreshes (_inFlight map, epg_providers.dart:183-202), so the only writers racing readers are the periodic provider reads. High is exaggerated for a self-healing cache; medium for the recurring transient blank-guide window.

### MEDIUM-9: XML encoding declaration ignored, non-UTF-8 XMLTV feeds (ISO-8859-1) fail the whole refresh

Location: `lib/features/epg/data/parsers/xmltv_parser.dart:25`  
Category: bug | Verifier confidence: high

Impact: Latin-1/Windows-1252 XMLTV feeds, still common from European providers, fail entirely the moment a single accented character appears, and the user sees a misleading 'Invalid EPG format' error for a feed that is valid per its declared encoding.

## Refuted candidates (for the record)

These were reported by finder agents but did not survive adversarial verification:

- Program progress bars are computed from DateTime.now() at build time and never tick: Refuted. The claim says no periodic timer drives rebuilds, but epg_providers.dart:48-60 defines minuteTickProvider (a StreamProvider emitting on every minute boundary), and both currentProgramProvider (line 124) and nextProgramProvider (line 132) watch it, re-executing every minute. MiniPlayer watches currentProgramProvider/nextProgramProvider in build (mini_player.dart:36-39), and PlayerScreen._buildBottomBar does the same (player_screen.dart:565-577); each minute tick transitions the FutureProvider through loading-to-data states, notifying watchers and rebuilding the widgets, so _buildProgressBar recomputes DateTime.now() at minute granularity. A program progress bar advancing once per minute is the intended design (see the provider's own doc comment) and is not frozen 'for the entire program'. The 'NOW/UP NEXT' providers likewise refresh on the tick, not on incidental rebuilds.

- searchResultsProvider uses ref after its own disposal when the Search screen closes during the 250ms debounce, producing an unhandled StateError: Refuted by the installed Riverpod 2.6.1 source. In ~/.pub-cache/hosted/pub.dev/riverpod-2.6.1/lib/src/framework/element.dart, ref.read/ref.watch after element disposal have no disposal guard: read() only runs _assertNotOutdated (a debug assert about _didChangeDependency, not disposal) and _debugAssertCanDependOn (circular-dependency assert), then delegates to _container.read. The 'Cannot use Ref after it has been disposed' StateError is Riverpod 3.x behavior; the only disposal StateError in 2.6.1 is on the ProviderContainer itself (container.dart:422), which stays alive. Furthermore, when the Search screen closes, the autoDispose searchQueryProvider is also disposed and recreated as '' on the post-dispose ref.read, so line 131's guard ('' != query, since query.length >= 2) returns [] immediately and the body never even reaches ref.watch. The abandoned future completes normally with [], producing no unhandled exception. The debounce-cancel design works as intended on Riverpod 2.x.

- Group index drifts when a channel's group is cleared, and getChannelsByGroup never re-verifies, The code asymmetry exists (saveChannel line 216 skips updateIndex when the new group is empty, and getChannelsByGroup lines 309-318 does not re-check channel.group like getFavoriteChannels re-checks isFavorite at line 281), but the defect is unreachable. saveChannel has exactly two callers (playlist_repository_impl.dart:265 updateChannel and :292 toggleFavorite). toggleFavorite uses copyWith(isFavorite:...) and never changes group, so oldGroup == newGroup always. updateChannel has zero callers anywhere in lib/ or test/ (grep confirms only the interface declaration and implementation). All real group changes flow through saveChannels/deleteChannels, which call _rebuildChannelIndexes and fully rebuild the group index. Even a stale index entry pointing at a deleted key returns null from box.get and is filtered at line 313-316. Latent hardening gap only; the claimed user-visible impact cannot occur with current callers.

- TV Guide date picker uses ref after await without a mounted check, The code pattern is as described (lines 994-1016: await showDatePicker, then ref.read with no mounted check), and ref-after-dispose would throw in a ConsumerState. But I could not find a reachable path that disposes TvGuideScreen while the dialog is open AND returns a non-null date. The dialog's modal barrier blocks all pointer interaction with the sidebar/shell beneath it, so the user cannot navigate away; the system back button or barrier tap dismisses the dialog returning null, which is guarded by 'if (date != null)'. The in-screen listeners (goToNowTrigger, epgRefreshNotifier) only scroll, never navigate, and AppShell auto-refresh does not route. No deep-link handler that re-routes the shell while a dialog is open was identified. Single-threaded event-loop semantics mean no disposal can interleave between the dialog popping with a date and the ref.read resuming. So this is a latent lint-grade omission, not a demonstrably reachable defect. Low confidence because an unexamined external navigation trigger (e.g. a future deep link) would make it real.
